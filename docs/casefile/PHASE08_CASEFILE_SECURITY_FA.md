1. همان منطق موجود حفظ شد: ADMIN و ایجادکننده پرونده می‌توانند مدیریت کنند؛ عضو فعال فقط حق خواندن دارد. `CASE_READ` و `CASE_WRITE` همچنان باید در لایه HTTP احراز شوند.

3. `TESTER` و رکوردهای `TEST` از APIهای معمولی `REAL` جدا باقی می‌مانند. هیچ مسیر تازه‌ای برای نوشتن آزمایشی اضافه نشده است.
4. عضویت عادی اجازه ویرایش، دعوت، لغو عضویت یا مدیریت سایر افراد نمی‌دهد.

## کنترل هم‌زمانی و ETag

- هنگام `PUT /api/v1/cases/{id}`، `CaseRepository.findByIdForUpdate` قفل `PESSIMISTIC_WRITE` می‌گیرد. این قفل عملیات هم‌زمان را سریالی می‌کند؛ **جایگزین کامل Optimistic Locking نسخه‌دار نیست**.
- پاسخ `GET /api/v1/cases/{id}`، Header استاندارد `ETag` دارد.
- یک کلاینت می‌تواند در `PUT` مقدار آخرین ETag دریافت‌شده را در Header `If-Match` بفرستد. اگر تغییر دیگری رخ داده باشد، HTTP `412` برگشت داده می‌شود؛ هیچ Mutation و Audit موفق ثبت نمی‌شود.
- کلاینت‌های قدیمی می‌توانند بدون `If-Match` به کار ادامه دهند؛ برای آن‌ها تشخیص Lost Update سمت کاربر تضمین نمی‌شود. توصیه: در UI فاز بعد، `If-Match` اجباری شود و UX تعارض پیاده شود.
- زمان‌های به‌روزرسانی به میکروثانیه گرد می‌شوند تا با دقت پیش‌فرض PostgreSQL هم‌خوان شوند. **کفایت آن در Runtime باید آزموده شود.**

## lifecycle

- وضعیت `ARCHIVED` در API ویرایش عمومی فقط‌خواندنی است. تلاش برای تغییر پرونده بایگانی‌شده با `409` رد می‌شود.
- گذار از سایر وضعیت‌ها به `ARCHIVED` با همان PUT قبلی حفظ می‌شود.
- سایر گذارهای تاریخی بدون محدودیت جدید مانده‌اند؛ قرارداد نهایی موتور وضعیت‌های کسب‌وکار باید در فاز اختصاصی تعیین شود.
- Audit موفق `CASE_CREATED` / `CASE_UPDATED` طبق اصلاح Phase06 در همان تراکنش کسب‌وکار مشارکت می‌کند. تاریخچه رویدادهای ناموفق و ردشده جدا باید طراحی شود.

## فهرست پرونده‌ها

- SQL به‌صورت مستقیم `REAL` و creator/admin/active membership را فیلتر می‌کند، سپس دفاع دوم `CaseAccessService.canRead` حفظ می‌شود.
- `GET /api/v1/cases` همچنان Array قدیمی برمی‌گرداند؛ pagination در قرارداد فعلی نیست. برای کارایی در تعداد زیاد پرونده، تغییر API نسخه‌دار یا pagination اختیاری لازم است.
- Query روی جدول‌های فعلی کار می‌کند؛ **هیچ Migration در بسته اجرا یا تولید نمی‌شود**.

## شواهد و وضعیت اعتبارسنجی

- تست‌های `Phase08*Test.java`: Mockito/JUnit برای RBAC، IDOR، archive، stale revision، قفل ردیفی، validation عضویت و Headerهای ETag.
- `Verify` با Maven آفلاین `mvn -o -pl modules/casefile -am test` اجرا می‌شود.
- Testcontainers، JDBC با دو تراکنش واقعی PostgreSQL، HTTP و مرورگر، کنترل RLS/TEST workspace، آزمون کنسول و دیتابیس کلون‌شده **BLOCKED / NOT EXECUTED** تا اثبات محیط ایزوله. موفقیت Maven به معنای موفقیت این آزمون‌ها نیست.
- تغییرات Phase07 / Phase06 قبلاً باید در baseline باشد؛ نصب‌کننده روی فایل‌های تغییرکرده یا SHA مبنای نامعتبر متوقف می‌شود.
- خطر باقی‌مانده: متدهای خارج از مسیر case مانند دسترسی مستند صرفاً بر اساس UUID باید جداگانه بررسی شوند؛ DocumentService فعلاً Guard اختصاصی دارد.

## اجرای امن

Launcher PowerShell 5.1 فایل ZIP را از Downloads خودکار استخراج می‌کند، SHA بسته را کنترل می‌کند و صرفاً سورس را تغییر می‌دهد. بک‌آپ خارج از مخزن ساخته می‌شود و Rollback فقط وقتی مجاز است که فایل‌ها پس از نصب تغییر نکرده باشند.
