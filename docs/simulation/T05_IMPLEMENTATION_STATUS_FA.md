## پیش‌نیازهای امنیتی

- PostgreSQL از قبل باید V58 و V59 را داشته باشد؛ دو Migration افزایشی V60 و V61 **با نخستین راه‌اندازی Backend بعد از نصب** اجرا می‌شوند.
- بک‌آپ و تست روی نسخه قابل بازیابی دیتابیس الزامی است.
- نقش **runtime** برنامه نباید `SUPERUSER` یا `BYPASSRLS` داشته باشد؛ تشخیص در `/api/v1/admin/simulations/core-fixture-readiness` انجام می‌شود. در محیطی که `POSTGRES_USER` خود نقش مدیر PostgreSQL است، ایجاد Fixture عمداً BLOCKED می‌ماند.
- نصب‌کننده فقط **فایل‌های سورس** را بازگردانی می‌کند؛ تغییرات Flyway در DB را Rollback نمی‌کند.
- تغییر حالت سرور، Spring Profile و داده‌های دیگر کاربران توسط اسکریپت انجام نمی‌شود.
- `100%` در Preflight قبلی فقط تعداد گام‌های تمام‌شده است. Fixture چهارجدولی نیز به معنی PASSED شدن E2E-14 کامل نیست.

## نحوه آزمون بعد از Build و راه‌اندازی

۱. وارد `/admin/simulations` با حساب دارای `USER_MANAGE` شوید.
۲. از «داده‌ها و شواهد» وضعیت T05 را بخوانید. اگر نقش PostgreSQL نامحدود باشد، دکمه به درستی غیرفعال است.
۳. فضای آزمایشی انتخاب کنید؛ دکمه «ایجاد و اعتبارسنجی پرونده TEST» یک Fixture مصنوعی تولید می‌کند.
۴. شناسه‌های پرونده، ملک و دو مالک در همان صفحه نمایش داده می‌شوند. نتایج از PostgreSQL در تراکنش‌های دارای Scope معتبر بازیابی می‌شوند.
۵. API معمول پرونده در حالت REAL نباید مورد جدید را بازگرداند؛ در صورت مشاهده نشت، فوراً اجرای TEST را متوقف کنید.

## آزمون‌های تکمیلی پیشنهادی

- تحت نقش غیر SUPERUSER، یک رکورد TEST را از Query معمول REAL بخوانید؛ باید ۰ ردیف باشد.
- درون TEST workspace A تلاش برای ارجاع به پرونده TEST workspace B یا REAL باید رد شود.
- درخواست TEST بدون workspace معتبر باید رد شود.
- تغییر مستقیم `data_scope` یا `test_workspace_id` یک رکورد باید رد شود.
- در حالت تست `notification_outbox` و `crawl_job` نباید رکورد TEST بپذیرند.
- PostgreSQL Role Owner، Connection Pool، توابع با `SECURITY DEFINER` و دسترسی DBA باید جداگانه ممیزی شوند.
