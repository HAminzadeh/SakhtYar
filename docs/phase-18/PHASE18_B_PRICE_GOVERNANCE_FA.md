# Phase 18-B — موتور قیمت و حاکمیت مصالح
مبنا: `v2 @ bc47498e25af5bfc274835c153ad61ec9e73fb95` (2026-11-28T04:48:14Z). V69 در CI قبلی موفق شد، ولی تست نقش محدود و HTTP اختصاصی هنوز تأیید نشده است. این بسته 18-B را با migration افزایشی V70 و اصلاح موضعی Redis YAML آماده می‌کند؛ هیچ Commit/Push یا اجرای DB انجام نمی‌دهد.

## سیاست دامنه (تصمیم طراحی)
- `amount` مبلغ کل برای `quantityBasis` در `unitCode` است. داده خام در مشاهده اصلی باقی می‌ماند. قیمت هر واحد پایه = مبلغ تبدیل‌شده ÷ مقدار تبدیل‌شده؛ تبدیل واحد با MaterialFoundation و ضریب دقیق، تقسیم DECIMAL128، خروجی آمار با scale=2/HALF_UP و رد صفر گرد‌شده یا overflow. نوع و برند/Variant و منطقه با کلید جدا حفظ می‌شوند. تبدیل بسته/چگالی بدون ضریب معتبر ممنوع. واحدهای legacy ناشناخته و مشاهدات فاقد currency_id معتبر منتشر نمی‌شوند.
- ریال و تومان از قرارداد V26/Globalization موجود استفاده می‌کنند: 1 TOMAN = 10 IRR. گروه ایرانی مشترک و دو نمایش ارزی مستقل در صورت فعال بودن ارز و قابل نمایش بودن آمار؛ تعداد نمونه در هر نمایش یک مجموعه واحد است، جمع کردن sampleCount دو نمایش اشتباه است. سایر ارزها در گروه جدا می‌مانند؛ هیچ نرخ FX خارجی تخمین زده نمی‌شود. تبدیل ارزهای دیگر با نرخ ثبت‌شده و تأییدشده خارج از دامنه این بسته است.
- زمان مشاهده حداکثر now و حد پایین 1900، ذخیره microseconds مطابق PostgreSQL. تازگی 30×24 ساعت و حداقل confidence=0.50، null/کمتر خارج از مرجع، اما به عنوان مشاهده قابل نگهداری است. این اعداد سیاست پیشنهادی نسخه 2.0 هستند و اعتبارسنجی تجربی بازار ندارند. تاریخ انقضای انتشار = قدیمی‌ترین نمونه + 720h (محافظه‌کارانه). حداقل یک نمونه مجاز؛ sampleCount صریح است و این به معنی قیمت کارشناسی قطعی نیست.
- منبع باید موجود، enabled و هم‌Scope با مصالح باشد. currency_code باید در global_currency فعال باشد (V26 همچنان مرجع). لینک فقط HTTP/HTTPS بدون credentials، بدون fetch. CRAWLER/API نیازمند URL؛ IMPORT نیازمند URL یا rawPayload. SYSTEM در ارسال HTTP/سرویس قیمت ممنوع؛ originهای دیگر ادعای ثبت‌کننده مجاز هستند، اثبات اتصال واقعی Collector نیستند. منبع enabled به تنهایی گواه اعتبار علمی نیست؛ human review و confidence لازم است. trust_level آزاد منبع، بدون قرارداد مصوب، مبنای whitelist اختراعی قرار نگرفته است.
- شهر بدون استان رد؛ نرمال‌سازی فارسی با MaterialFoundation و case-insensitive، بدون ترکیب شهر/استان/نوع قیمت/Variant. این قرارداد بر رشته استوار است؛ Geo ID و حوزه جغرافیایی بین‌کشوری و قواعد اختصاصی منبع در آینده قابل تکمیل است.
- idempotency طبیعی: SHA256 با length-prefix روی material, variant, type, ارز گروه, واحد پایه, مبلغ کل و مقدار تبدیل‌شده دقیق، استان/شهر، source, timestamp microseconds. ثبت معادل ریال/تومان یا تن/کیلوگرم برای همان مقدار و مبلغ و زمان/منبع یک quote است. ارسال مجدد همان شواهد همان ID را بازمی‌گرداند؛ اختلاف URL/origin/rawPayload/confidence با همان quote رد می‌شود. legacy با source/time جست‌وجو و در تجمیع dedup می‌شود؛ هیچ حذف/backfill خودکار ندارد. ثبت‌های واقعی جدید با زمان/منبع متفاوت مستقل‌اند. این natural idempotency است نه header اختصاصی Idempotency-Key. Unique index + قفل والد برای concurrency سرویس؛ direct SQL با hash ساختگی از API معتبر محسوب نمی‌شود.

## گردش تصمیم
- PENDING_REVIEW → APPROVED / REJECTED؛ APPROVED → REJECTED (ابطال)؛ REJECTED نهایی؛ درخواست همان وضعیت بدون تغییر شواهد idempotent. ثبت/بازبینی نیازمند USER_MANAGE و principal واقعی، علت تصمیم غیرخالی، actor و timestamp. از رکورد ردشده برای تأیید مجدد استفاده نشود؛ شواهد اصلاح‌شده به عنوان quote تازه ثبت شود.
- anomaly: median-deviation موجود، حداقل سه نمونه پیشین هم‌گروه و واجد شرایط، آستانه 50% و 100% حفظ می‌شود. مبنا مقادیر نرمال‌شده است، نه مبلغ خام؛ میانه بدون گرد کردن و آستانه با مقایسه دقیق تعیین می‌شود. نمونه‌های هم‌زمان/آینده از تاریخچه قبلی حذف، بررسی مجدد ترتیب زمانی در rebuild برای legacy/backdated. score بیش از ظرفیت 10,4 محدود می‌شود؛ هشدار HIGH باقی می‌ماند. OPEN و ACCEPTED (تأیید واقعی بودن ناهنجاری) حذف از مرجع؛ DISMISSED (رد هشدار) تنها اجازه بازگشت مشروط است. وضعیت نهایی قابل بازنویسی نیست. با کمتر از سه نمونه قبلی تضمین تشخیص پرت وجود ندارد.
- با تغییر review/anomaly انتشار جاری آن مصالح retire می‌شود؛ برای انتشار دوباره rebuild اجباری است. API فعلی `/aggregates` فقط مرجع جاری واجد شرایط، endpoint جدید `/api/v1/materials/{id}/aggregates/history` با `aggregate`, `usable`, `expiresAt`, `evidenceIds` تاریخچه می‌دهد. `/aggregates/rebuild` نسخه جدید ایجاد می‌کند؛ بازسازی بدون تغییر مجموعه شواهد IDهای فعلی را حفظ می‌کند. هر snapshot قبلی به ID خود متصل می‌ماند. V70 همه aggregateهای legacy را به صورت پیش‌فرض غیرجاری می‌بیند؛ اپراتور مجاز باید مجدداً مرجع را بسازد، بدون تولید قیمت ساختگی. اگر داده واجد شرایط نیست، مصرف قیمت باید fail closed باشد.
- Assembly همان متد repository سابق را استفاده می‌کند ولی query جدید فقط مرجع جاری و واجد شرایط با source/currency/observation/anomaly فعال و انقضا برمی‌گرداند. نام API/DTO قبلی حفظ می‌شود، semantics تاریخچه عمداً به endpoint مستقل منتقل شده. Scenario و Feasibility منطق تجاری جدید دریافت نمی‌کنند؛ تست end-to-end و race در C.
